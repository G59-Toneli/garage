# Evaluation runs in two layers: a deterministic CI gate and an on-demand judge

Retrieval quality is fully deterministic — given a fixed corpus, query and embedder, `recall@k`, MRR
and nDCG return the same value every time and need no language model to compute. Generation quality
is not. Collapsing both into one evaluation run would make the cheap, reproducible half depend on
the expensive, variable half. So they are separated: a **deterministic gate** runs on every commit
in CI, costs nothing, and fails the build on retrieval regression; a **judge-based evaluation** of
grounding, citation accuracy and abstention runs on demand and commits its output as a Run Record.

## Consequences

- The argument for fine-tuning lives entirely in the deterministic layer, which is the layer anyone
  can reproduce. This is deliberate.
- The judge runs locally against the author's existing Claude Code session rather than in CI with an
  API key. This is a cost decision, made under the zero-cost constraint of ADR-0001, and is stated
  as such rather than disguised as a technical one.
- The judge is cross-family with respect to the generator (Gemini generates, Claude judges) to avoid
  self-preference bias.
- **A judge's verdicts are not reported until its agreement with human labels has been measured and
  published.** An uncalibrated judge trades one unknown bias for another.
- Evaluation sets are written by a human and never generated by the same model that produces
  training data, so that measurement is not contaminated by the generator's own phrasing.
- Nothing stochastic is ever published as a point value: each question runs `n` times and the
  interface shows the spread. Hiding variance in a system built to prove measurement would
  contradict the whole project.
